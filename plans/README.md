## Deferred deliberately

- Transactional outbox, idempotent consumers, retry and dead-letter topics: required when persisted business events are implemented, but unnecessary for the manual demo.
- Generic `EventBus`/publisher interface: one adapter is a hypothetical seam; introduce it only when a second real adapter or outbox publisher exists.
- JSON event schemas/schema registry: String key/value keeps the current demo minimal.
- Production Kafka security, monitoring, retention tuning, and clustering: separate deployment work.
- CI/formatter/static-analysis additions: lower leverage until the broker migration and deterministic tests are complete.

## High-risk finding outside this Kafka plan set

- Tracked JWT signing secrets and a local database credential location were found during audit. Values are intentionally not reproduced. Rotate exposed credentials and move them to validated environment-backed configuration in a separate security plan before deployment.

## Findings considered and rejected

- Keep both RabbitMQ and Kafka “for flexibility”: rejected because no distinct use case exists and it doubles local/runtime infrastructure.
- Put all publishers and consumers in a shared `messagings` package: rejected for production code because it leaks transport/topic concerns across feature seams; acceptable only as a disposable tutorial spike.
- Implement outbox in the first demo: rejected because it obscures the producer/topic/consumer learning path and expands scope before notification persistence exists.
